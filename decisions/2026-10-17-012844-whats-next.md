# Picking the next issue with `/whats-next`

Issue: #38

`/whats-next` is for picking a project back up after a break or a finished piece of work: from a clean, up-to-date default branch, one subagent reads the open issues and recommends the next one, with the command to run.

Choices worth remembering:

- **The name.** `/status` was the first idea, but Claude Code has a built-in `/status`, and a skill with the same name would clash with it.
- **The scope was narrowed while planning.** The first draft of #38 ran three subagents (recent work, in-flight branches and local state, open issues) and reported on all of it. Skye cut it back to the question she actually asks: "what do I do now?" Assuming a clean, up-to-date default branch, and stopping if it isn't, removes all the local-state reporting.
- **The stage is worked out each time, not stored.** Stage labels on issues (`to-plan`, `to-build` and so on, set by each workflow skill) were considered and dropped: they'd be a second copy of what the plan and handover comments, branches and PRs already show, and could drift from it.
- **Two passes.** One REST call lists every open issue with its labels, sub-issue count and blocked-by count, and GitHub search (`"Plan (approved)" in:comments`) finds the planned ones. Comments are read only for the shortlist, so a project with many issues costs about the same as one with a few.
- **No `/setup-project` needed.** Most skills stop when `workflow.md` is missing, rather than guess a command. This one only needs the default branch, which GitHub reports exactly (`gh repo view`), so asking it isn't a guess, and the skill works in any repo with issues.
- **At most 5 issues shown,** plus a count of the rest. It's a path forward, not a full triage.
- **Only Skye starts it,** though it changes nothing: it runs a subagent, which takes time and tokens, and the moment to ask is hers.

Left out: a summary of recent work, a survey of in-flight branches, flagging stale or duplicate issues, and stage labels.
